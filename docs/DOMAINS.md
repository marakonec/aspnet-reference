# Каталог індивідуальних предметних областей

Каталог до лабораторних робіт дисципліни «ASP.NET технології», 2026/27 навчальний рік. Бланк паспорта предметної області лежить у файлі `docs/templates/DOMAIN.md`, заповнений приклад для еталона у файлі `docs/DOMAIN.md`. Порядок роботи з ним описано в лабораторній роботі 1 методичних рекомендацій.

Каталог — вхідний артефакт ЛР1: здобувач обирає з нього домен і заповнює за ним паспорт. Усі дані в проєктах — умовні й генеруються скриптом; жоден домен не потребує персональних даних реальних осіб (там, де в предметній області є люди, у моделі лишається обліковий або табельний номер без прізвища).

---

## 0. Як користуватися

**Вибір.** Домен закріплюється за здобувачем до захисту лабораторної роботи 1. Два здобувачі однієї групи не беруть один домен; якщо каталог вичерпано, наступні беруть власні домени за правилом нижче.

**Власний домен.** Здобувач може запропонувати свій, якщо для нього можна заповнити всі рядки паспорта домену, ключова операція змінює щонайменше три сутності (або дві й лічильник) в одній транзакції, є сценарій конкурентності, дві ролі й «своє», і він не є доменом еталона. Пропозиція подається у формі паспорта; рішення — до видачі лабораторної роботи 1, бо після третьої лекції предметну область уже не міняють.

**Заміна.** Захист лабораторної роботи 1 — єдине місце, де вибір ще можна виправити без втрат: якщо ключова операція вироджується в оновлення одного рядка, лабораторних робіт 2–4 не буде на чому робити.

**Чого в каталозі немає навмисно.** Інтернет-магазинів, бібліотек, соціальних мереж і всього, що має готовий навчальний приклад із кодом у мережі: така робота не перевіряється на захисті, бо не відрізняється від знайденої. Немає й домену еталона («Прокат вимірювальних приладів») та його перейменувань.

**Що в каталозі є навмисно спільного.** Усі двадцять доменів мають однаковий кістяк: сутність зі станом, лічильник або залишок, операція, що змінює три сутності в одній транзакції, і два рівні доступу. Це не бідність фантазії, а вимога курсу: без лічильника немає втраченого оновлення, без стану немає що описувати ресурсом, без «свого» ресурсу немає політики в лабораторній роботі 3. Відрізняються домени природою обмеження й тим, що саме в них дорого порушити.

**Шляхи ресурсів.** Шляхи на кшталт `GET /sidings` чи `POST /shunting-orders/{id}/place` наведено як орієнтир форми, а не як контракт: остаточні імена ви фіксуєте в лабораторній роботі 1 у контракті й у `selfcheck.json`. У каталозі вони потрібні лише для того, щоб було видно, яка операція неідемпотентна і який ресурс кешується.

## 1. Шкала складності

| Оцінка | Що означає |
|---|---|
| ★☆☆ | Один інваріант (один лічильник або одна місткість). Модель прозора, конкурентність очевидна з першого погляду. |
| ★★☆ | Один інваріант плюс похідні дані (підсумок, історія, стан, що залежить від лічильника) або обмеження на двох сутностях. |
| ★★★ | Два-три незалежні інваріанти, що мають утриматися в одній транзакції, або похідні дані, які перераховуються для багатьох рядків одразу. |

Розкид навмисно вузький. Усі двадцять доменів потребують однакового часу на лабораторну роботу 1: різниця між ★ і ★★★ — у кількості інваріантів, які треба втримати, а не в обсязі коду. ★★★ варто брати тому, хто хоче цікавішого матеріалу для лабораторної роботи 2 і ADR; ★☆☆ — тому, хто хоче гарантовано вкластися.

**Розподіл:** ★☆☆ — 3 домени, ★★☆ — 13, ★★★ — 4.

## 3. Домени

### 1. Подача вагонів на під'їзну колію

*Природа: транспорт (залізниця). Складність: ★★☆*

Вантажний фронт підприємства приймає вагони групами: диспетчер формує маневрове завдання й подає групу на колію обмеженої корисної довжини. Система веде стан кожного вагона, зайнятість колій і журнал подач та забирань.

**Сутності**

- `Siding` (колія) — код, корисна довжина в умовних вагоно-одиницях, зайнято одиниць, режим роботи, стан
- `Wagon` (вагон) — умовний номер, рід, довжина в одиницях, стан, поточна колія
- `Consignor` (вантажовласник) — код, назва, контактний телефон
- `ShuntingOrder` (маневрове завдання) — номер, плановий час, стан, автор
- `OrderItem` (позиція завдання) — завдання, вагон, порядок у групі
- `PlacementRecord` (запис подачі) — вагон, колія, завдання, час подачі й забирання

| Рядок паспорта | Значення |
|---|---|
| «Один до багатьох» | `Consignor` → `Wagon` (закріплені вагони) |
| «Багато до багатьох» | `ShuntingOrder` ↔ `Wagon` через `OrderItem` |
| Ключова операція | `POST /shunting-orders/{id}/place` — подати групу вагонів на колію |
| Що змінюється в одній транзакції | стан `ShuntingOrder` → `Placed`; `Siding.OccupiedUnits` += сумарна довжина групи; `Wagon.State` і колія для кожного вагона; новий `PlacementRecord` |
| Сценарій конкурентності | двоє диспетчерів подають різні завдання на ту саму колію, де лишилося місце на один вагон: обидва бачать «вільно», після обох подач зайнято більше, ніж є |
| Ідемпотентна операція | `PUT /sidings/{code}/mode` — встановити режим роботи колії |
| Неідемпотентна | подача: повторний виклик — це друга подача, а не та сама |
| Ролі | `dispatcher` — планує і подає будь-що; `consignor-clerk` — бачить і створює завдання лише на вагони свого вантажовласника; `auditor` — лише журнал подач |
| Що означає «своє» | `Wagon.ConsignorId` збігається з ідентифікатором вантажовласника в токені |
| Кешований ресурс | `GET /sidings` — паспорт колій і довідник родів вагонів |
| Некешований | `GET /sidings/{code}/occupancy` — поточна зайнятість, за нею ухвалюють рішення про подачу |
| Навантаження на читання | за півгодини до зміни десятки планувальних екранів і табло оновлюють план: паспорт колій читається сотні разів за хвилину, а змінюється раз на місяць |
| Зовнішня залежність | сповіщення вантажовласника про подачу (шлюз повідомлень, у репозиторії курсу заглушка) |
| Чутливий атрибут | `Consignor.Phone` |
| Сутність зі станом | `ShuntingOrder`: `Draft → Planned → Placed → Released / Cancelled` |

### 2. Крос-докінг на перевантажувальному терміналі

*Природа: логістика. Складність: ★★☆*

Термінал приймає вхідні партії, розсортовує місця вантажу по воротах відправлення і формує вихідні рейси без проміжного зберігання. Система стежить, яке місце до якого рейсу приписане і чи вистачає місткості машини.

**Сутності**

- `Carrier` (перевізник) — код, назва, контактний телефон водія
- `InboundShipment` (вхідна партія) — номер, перевізник, час прибуття, стан
- `Package` (вантажне місце) — код, вага, обсяг в умовних одиницях, стан, вхідна партія
- `Dock` (ворота) — код, напрямок, стан
- `OutboundRun` (вихідний рейс) — номер, ворота, плановий час, місткість в одиницях, завантажено одиниць, стан
- `LoadItem` (завантаження) — рейс, місце, час сканування

| Рядок паспорта | Значення |
|---|---|
| «Один до багатьох» | `InboundShipment` → `Package` |
| «Багато до багатьох» | `OutboundRun` ↔ `Package` через `LoadItem` (місце може бути перезаписане на інший рейс — історія лишається) |
| Ключова операція | `POST /outbound-runs/{id}/load` — завантажити набір місць у рейс |
| Що змінюється в одній транзакції | `OutboundRun.LoadedUnits` += обсяг і стан рейсу; `Package.State` → `Loaded` для кожного місця; нові `LoadItem`; `InboundShipment.State` → `Closed`, якщо це було останнє місце партії |
| Сценарій конкурентності | два комірники сканують останні місця в рейс, де лишилася місткість на одне: машина «завантажена» понад місткість |
| Ідемпотентна операція | `PUT /docks/{code}/state` — встановити стан воріт |
| Неідемпотентна | завантаження: повторне сканування того самого місця — це друга спроба зайняти місткість |
| Ролі | `terminal-operator` — вантажить будь-який рейс; `carrier-clerk` — бачить лише рейси свого перевізника; `auditor` — лише читання журналу |
| Що означає «своє» | `OutboundRun.CarrierId` збігається з ідентифікатором перевізника в токені |
| Кешований ресурс | `GET /docks` і `GET /carriers` — довідники воріт і напрямків |
| Некешований | `GET /outbound-runs/{id}/capacity` — вільна місткість рейсу |
| Навантаження на читання | під час зміни термінальні сканери перечитують довідник воріт і напрямків перед кожним скануванням — тисячі читань проти десятків змін на добу |
| Зовнішня залежність | підтвердження часу прибуття в системі перевізника (заглушка) |
| Чутливий атрибут | `Carrier.DriverPhone` |
| Сутність зі станом | `OutboundRun`: `Planned → Loading → Sealed → Departed / Cancelled` |

### 3. Змінні наряди комунального автопарку

*Природа: транспорт, комунальні служби. Складність: ★☆☆*

Диспетчер парку на кожну зміну закриває наряд: машина, табельна позиція водія і маршрут. Система не дає видати одну машину двічі й веде залишок мотогодин до найближчого обслуговування.

**Сутності**

- `Vehicle` (машина) — гаражний номер, тип, залишок мотогодин до обслуговування, стан
- `DriverSlot` (табельна позиція водія) — табельний номер, категорія допуску, доступність на зміну, службовий телефон
- `Route` (маршрут) — код, зміна, нормативна тривалість, тип машини
- `Shift` (зміна) — дата, номер, кількість відкритих нарядів, стан
- `Assignment` (наряд) — зміна, машина, позиція водія, маршрут, час видачі й закриття, відпрацьовано годин, стан

| Рядок паспорта | Значення |
|---|---|
| «Один до багатьох» | `Route` → `Assignment` |
| «Багато до багатьох» | `Shift` ↔ `Vehicle` через `Assignment` |
| Ключова операція | `POST /shifts/{id}/assignments` — видати наряд на зміну |
| Що змінюється в одній транзакції | новий `Assignment`; `Vehicle.State` → `OnRoute`; `DriverSlot.Availability` → зайнято; `Shift.OpenAssignments` += 1 |
| Сценарій конкурентності | два диспетчери видають останню справну машину потрібного типу на два різні маршрути |
| Ідемпотентна операція | `PUT /vehicles/{n}/state` — поставити машину на ремонт або зняти з ремонту |
| Неідемпотентна | закриття наряду: списує відпрацьовані мотогодини із залишку, повторний виклик списує вдруге |
| Ролі | `dispatcher` — видає і закриває будь-які наряди; `driver` — бачить лише власні наряди; `mechanic` — змінює лише стан машин, нарядів не бачить |
| Що означає «своє» | `Assignment.DriverSlotId` збігається з табельним номером у токені |
| Кешований ресурс | `GET /routes` — маршрутна сітка з нормативами (змінюється раз на квартал) |
| Некешований | `GET /vehicles/available?type=` — перелік справних вільних машин |
| Навантаження на читання | за двадцять хвилин до початку зміни всі термінали й табло парку разом тягнуть маршрутну сітку |
| Зовнішня залежність | довідка про погодні обмеження для допуску маршруту (заглушка) |
| Чутливий атрибут | `DriverSlot.Phone` |
| Сутність зі станом | `Assignment`: `Issued → OnRoute → Closed / Cancelled` |

### 4. Постановка суден до причалу річкового порту

*Природа: транспорт (водний). Складність: ★★☆*

Порт планує підхід суден до причалів, обмежених довжиною стінки й прохідною осадкою. Диспетчер ставить судно до причалу, веде вантажні операції і звільняє причал після відходу.

**Сутності**

- `Berth` (причал) — код, довжина стінки, прохідна осадка, зайнято метрів, стан
- `Vessel` (судно) — умовний реєстровий номер, довжина, осадка, агент, стан
- `Agent` (судновий агент) — код, назва, контактний телефон
- `PortCall` (заход) — судно, плановий час, стан
- `BerthAllocation` (постановка) — заход, причал, час швартування й відходу
- `CargoOperation` (вантажна операція) — заход, рід вантажу, планова кількість, виконано

| Рядок паспорта | Значення |
|---|---|
| «Один до багатьох» | `Agent` → `Vessel`; `PortCall` → `CargoOperation` |
| «Багато до багатьох» | `PortCall` ↔ `Berth` через `BerthAllocation` (перешвартування в межах одного заходу) |
| Ключова операція | `POST /port-calls/{id}/berth` — поставити судно до причалу |
| Що змінюється в одній транзакції | `PortCall.State` → `AtBerth`; `Berth.OccupiedLength` += довжина судна; `Vessel.State` → `Moored`; новий `BerthAllocation` |
| Сценарій конкурентності | два диспетчери ставлять різні судна до причалу, де лишилося тридцять метрів вільної стінки |
| Ідемпотентна операція | `PUT /berths/{code}/status` — вивести причал у ремонт або повернути в роботу |
| Неідемпотентна | постановка: повторний виклик займає довжину вдруге |

### 5. Міжопераційний рух партій на дільниці

### 10. Запис на вибіркові дисципліни

| Чутливий атрибут | `StudentRecord.Email` |

### 11. Розстановка занять по аудиторіях

*Природа: освіта. Складність: ★★★*

Диспетчер ставить заняття в клітинку розкладу, де одночасно мають бути вільні аудиторія, викладацька позиція і група. Розстановка займає клітинку для всіх трьох, збільшує лічильник навантаження викладача і створює рядок розкладу.

- `TimeSlot` (клітинка) — день тижня, номер пари, тиждень (чисельник або знаменник)

- `ScheduleEntry` (рядок розкладу) — клітинка, аудиторія, викладацька позиція, група, дисципліна, стан

| Рядок паспорта | Значення |
|---|---|
| «Один до багатьох» | `Discipline` → `ScheduleEntry`; `StudyGroup` → `ScheduleEntry` |
| «Багато до багатьох» | `TimeSlot` ↔ `Room` через `ScheduleEntry` |

| Що змінюється в одній транзакції | новий `ScheduleEntry`; клітинка позначена зайнятою для `Room`; `TeacherSlot.AssignedHours` += 2; клітинка позначена зайнятою для `StudyGroup` |
| Сценарій конкурентності | два диспетчери різних кафедр ставлять різні пари в ту саму аудиторію в тій самій клітинці — або, гірше, різні пари одному викладачеві |

| Кешований ресурс | `GET /schedule?group=&week=` — розклад групи на тиждень |
| Некешований | `GET /timeslots/{id}/free-rooms` — вільні аудиторії в клітинці |
| Навантаження на читання | перед початком пар розклад своєї групи відкривають усі водночас, а змінюється він кількома правками на тиждень |
| Зовнішня залежність | експорт розкладу в календарний сервіс (заглушка) |
| Чутливий атрибут | `TeacherSlot.Email` |
| Сутність зі станом | `ScheduleEntry`: `Draft → Published → Moved → Cancelled` |

Три незалежні інваріанти в одній транзакції (аудиторія, викладач, група не зайняті двічі) роблять цей домен найдорожчим у каталозі — і найцікавішим для ADR у ЛР2.

### 12. Планування зйомки дистанційного зондування

*Природа: наука. Складність: ★★★*

Замовники подають заявки на зйомку ділянок, а планувальник розкладає їх по витках, обмежених обсягом бортового запам'ятовувача і бюджетом енергії. Підтвердження заявки займає ресурс витка, створює завдання на борт і переводить заявку в план.

**Сутності**

- `AreaOfInterest` (ділянка) — код, умовні межі, пріоритет, останнє планування
- `Customer` (замовник) — код, організація, контактна адреса
- `ImagingRequest` (заявка на зйомку) — ділянка, замовник, режим зйомки, строк, стан
- `OrbitPass` (виток) — номер, час проходження, вільна пам'ять в одиницях, вільна енергія в одиницях, стан
- `TaskingItem` (завдання на борт) — заявка, виток, смуга, обсяг у одиницях пам'яті
- `Product` (продукт) — завдання, рівень оброблення, розмір, стан

| Рядок паспорта | Значення |
|---|---|
| «Один до багатьох» | `AreaOfInterest` → `ImagingRequest`; `TaskingItem` → `Product` |
| «Багато до багатьох» | `ImagingRequest` ↔ `OrbitPass` через `TaskingItem` |

| Сценарій конкурентності | два планувальники ставлять дві заявки на виток, де лишилося пам'яті на одну смугу |
| Ідемпотентна операція | `PUT /requests/{id}/priority` — встановити пріоритет заявки |
| Неідемпотентна | планування: повторний виклик списує бюджет витка вдруге |
| Ролі | `planner` — планує будь-які заявки; `customer-analyst` — бачить лише свої заявки і продукти; `operator` — підтверджує лише фактичне виконання зйомки |
| Що означає «своє» | `ImagingRequest.CustomerId` збігається з ідентифікатором замовника в токені |
| Кешований ресурс | `GET /passes?date=` — каталог витків на добу (розраховується раз, читається всіма) |
| Некешований | `GET /passes/{id}/budget` — залишок пам'яті й енергії витка |
| Навантаження на читання | аналітики замовників постійно перечитують каталог доступних вікон на найближчу добу, підбираючи час під свою ділянку |
| Зовнішня залежність | розрахунок геометрії витка зовнішнім сервісом ефемерид (заглушка) |
| Чутливий атрибут | `Customer.Email` |
| Сутність зі станом | `ImagingRequest`: `Draft → Submitted → Scheduled → Acquired → Delivered / Failed` |

Два незалежні бюджети витка (пам'ять і енергія) в одній транзакції — саме те місце, де токен конкурентності видно неозброєним оком.

### 13. Реєстр зразків керну геологічної партії

### 14. Рецензування доповідей конференції

Програмний комітет розподіляє анонімізовані доповіді між рецензентами з урахуванням секції і ліміту навантаження. Подання рецензії закриває призначення, перераховує зведений бал доповіді й зменшує лічильники відкритих рецензій.

| Навантаження на читання | у дні дедлайну сторінка прогресу відкрита в усіх рецензентів і оновлюється сама |

### 15. Показники лічильників і нарахування ОСББ

*Природа: комунальні служби. Складність: ★★★*

Мешканці подають показники квартирних лічильників, а система щомісяця закриває розрахунковий період і формує нарахування за тарифом, чинним на цей період. Закриття рахунку за період приймає показник, створює нарахування і зсуває баланс особового рахунку. Персональних даних немає: рахунок представлений умовним номером без прізвища.

**Сутності**

- `Account` (особовий рахунок) — умовний номер, квартира, площа, баланс, умовний платіжний реквізит, стан
- `Meter` (лічильник) — заводський номер, рахунок, вид ресурсу, останній показник, дата повірки, стан
- `Reading` (показник) — лічильник, період, значення, джерело (мешканець або контролер), стан
- `Tariff` (тариф) — вид ресурсу, період дії, ціна за одиницю
- `Charge` (нарахування) — рахунок, період, вид ресурсу, обсяг, сума
- `BillingPeriod` (розрахунковий період) — місяць, незакритих рахунків, стан

| Рядок паспорта | Значення |
|---|---|
| «Один до багатьох» | `Account` → `Meter`; `Meter` → `Reading` |
| «Багато до багатьох» | `Account` ↔ `Tariff` через `Charge` |
| Ключова операція | `POST /periods/{id}/accounts/{n}/close` — закрити рахунок за розрахунковий період |
| Що змінюється в одній транзакції | `Reading.State` → `Accepted` і `Meter.LastReading` оновлено; новий `Charge` за чинним тарифом; `Account.Balance` -= сума; `BillingPeriod.UnclosedAccounts` -= 1 |
| Сценарій конкурентності | контролер і мешканець подають показник за той самий період одночасно — два нарахування на один обсяг |
| Ідемпотентна операція | `PUT /meters/{n}/verification-date` — встановити дату наступної повірки |
| Неідемпотентна | закриття рахунку за період: повторний виклик нараховує вдруге |
| Ролі | `accountant` — закриває періоди і бачить усі рахунки; `resident` — подає показники й бачить баланс лише свого рахунку; `controller` — вносить показники за обходом, балансів не бачить |
| Що означає «своє» | `Account.Id` збігається з номером рахунку в токені |
| Кешований ресурс | `GET /tariffs` — чинні тарифи за видами ресурсів |
| Некешований | `GET /accounts/{n}/balance` — баланс рахунку |
| Навантаження на читання | в останні дні місяця кабінет мешканця відкривають тисячі разів, і тариф читається на кожному екрані, а змінюється раз на період |
| Зовнішня залежність | надсилання платіжного повідомлення (заглушка) |
| Чутливий атрибут | `Account.PaymentReference` |
| Сутність зі станом | `BillingPeriod`: `Open → Collecting → Closing → Closed`; `Reading`: `Draft → Submitted → Accepted / Rejected` |

Тариф діє на період, тому нарахування залежить від дати — це найлегше зіпсувати і найцікавіше описати в ADR.

### 16. Аварійно-диспетчерська служба водоканалу

*Природа: комунальні служби. Складність: ★★☆*

Диспетчер приймає заявки про пориви й відсутність води і направляє на них бригади, яких на дільниці обмежена кількість. Направлення переводить заявку в роботу, займає бригаду і, якщо порив аварійний, відкриває публічний запис про відключення.

**Сутності**

- `District` (дільниця) — код, межі, вільних бригад, черговий диспетчер
- `Crew` (бригада) — код, дільниця, склад, машина, стан
- `Incident` (заявка) — номер, умовна адреса, тип, пріоритет, телефон заявника, стан
- `Dispatch` (виїзд) — заявка, бригада, час виїзду й повернення, результат
- `Shutdown` (відключення) — дільниця, вид ресурсу, час початку й відновлення, перелік умовних адрес, стан

| Рядок паспорта | Значення |
|---|---|
| «Один до багатьох» | `District` → `Crew`; `District` → `Incident` |
| «Багато до багатьох» | `Incident` ↔ `Crew` через `Dispatch` (повторні виїзди, кілька бригад на одну заявку) |
| Ключова операція | `POST /incidents/{id}/dispatch` — направити бригаду на заявку |
| Що змінюється в одній транзакції | `Incident.State` → `InWork`; `Crew.State` → `OnSite` і `District.FreeCrews` -= 1; новий `Dispatch`; для аварійного типу — новий або оновлений `Shutdown` |
| Сценарій конкурентності | два диспетчери направляють останню вільну бригаду дільниці на дві різні заявки |
| Ідемпотентна операція | `PUT /incidents/{id}/priority` — встановити пріоритет заявки |
| Неідемпотентна | направлення: повторний виклик відкриває другий виїзд і вдруге займає бригаду |
| Ролі | `dispatcher` — працює із заявками своєї дільниці; `crew-lead` — закриває лише власні виїзди; анонімний відвідувач — читає лише перелік активних відключень |
| Що означає «своє» | `Incident.DistrictId` збігається з дільницею в токені; для `crew-lead` — `Dispatch.CrewId` |
| Кешований ресурс | `GET /shutdowns/active` — публічна сторінка відключень |
| Некешований | `GET /districts/{code}/free-crews` — вільні бригади дільниці |
| Навантаження на читання | після великого пориву публічну сторінку відключень відкриває півміста; вона ж має інвалідуватися в момент відновлення подачі — інакше люди читають неправду |
| Зовнішня залежність | оповіщення абонентів про відключення (заглушка) |
| Чутливий атрибут | `Incident.CallerPhone` |
| Сутність зі станом | `Incident`: `Registered → Assigned → InWork → Fixed → Closed` |

Єдиний домен каталогу, де кешований ресурс — публічний і читається анонімно: це дає найчистіший сценарій для лабораторної роботи 2 і окремий випадок «неавтентифікований доступ» для ЛР3.

### 17. Протокол туру аматорської ліги

*Природа: спорт. Складність: ★★☆*

Ліга проводить тури, і після кожного матчу суддя подає протокол із рахунком і картками. Затвердження протоколу закриває матч, зсуває рядки турнірної таблиці обох команд і застосовує дискваліфікації за накопиченими картками.

**Сутності**

- `Team` (команда) — код, назва, очки, забито, пропущено, стан
- `Round` (тур) — номер, дата, незакритих матчів, стан
- `Match` (матч) — тур, команда господарів, команда гостей, рахунок, суддя, стан
- `MatchEvent` (подія матчу) — матч, тип (гол, попередження, вилучення), хвилина, заявка гравця
- `RosterEntry` (заявка гравця) — команда, умовний код гравця, ігровий номер, попереджень, умовний номер заявочного документа, стан

| Рядок паспорта | Значення |
|---|---|
| «Один до багатьох» | `Round` → `Match`; `Match` → `MatchEvent`; дві зв'язки `Team` → `Match` (господарі й гості) сходяться на матчі |
| «Багато до багатьох» | `Team` ↔ гравець через `RosterEntry`; `Match` ↔ `RosterEntry` через `MatchEvent` |
| Ключова операція | `POST /matches/{id}/approve` — затвердити протокол матчу |
| Що змінюється в одній транзакції | `Match.State` → `Approved` із рахунком; рядки обох `Team` (очки, забито, пропущено); `RosterEntry.YellowCards` += і стан → `Suspended` при досягненні порогу; `Round.OpenMatches` -= 1 |
| Сценарій конкурентності | суддя і секретар ліги затверджують протокол одного матчу одночасно — очки нараховані двічі, таблиця розходиться з матчами |
| Ідемпотентна операція | `PUT /matches/{id}/venue` — встановити місце проведення |
| Неідемпотентна | затвердження протоколу: повторний виклик нараховує очки вдруге |
| Ролі | `league-admin` — затверджує і скасовує будь-який протокол; `referee` — подає протокол лише своїх призначених матчів; `team-manager` — бачить заявку і дискваліфікації лише своєї команди |
| Що означає «своє» | `Match.RefereeId` для судді; `RosterEntry.TeamId` для представника команди |
| Кешований ресурс | `GET /standings` — турнірна таблиця (публічна) |
| Некешований | `GET /matches/{id}` під час туру — поточний рахунок |
| Навантаження на читання | у вечір туру таблицю відкривають сотні вболівальників одночасно, а змінюється вона стільки разів, скільки матчів у турі |
| Зовнішня залежність | публікація результату в стрічку сайту ліги або месенджер (заглушка) |
| Чутливий атрибут | `RosterEntry.DocumentNumber` |
| Сутність зі станом | `Match`: `Scheduled → Played → ProtocolSubmitted → Approved / Disputed` |

Турнірна таблиця тут — похідні дані: її можна тримати як лічильники в `Team` або рахувати запитом. Вибір між цими двома варіантами і є ADR ЛР2.

### 18. Хронометраж багатоденної велогонки

*Природа: спорт. Складність: ★★☆*

Гонка складається з етапів, і після кожного секретаріат затверджує протокол із часом усіх учасників. Затвердження закриває етап, перераховує загальний і командний заліки й застосовує накладені штрафи.

**Сутності**

- `Stage` (етап) — номер, дата, довжина, тип, секретар, стан
- `Team` (команда) — код, назва, сумарний час трьох найкращих
- `Entry` (учасник) — стартовий номер, команда, сумарний час, очки, умовний номер ліцензії, стан
- `StageResult` (результат етапу) — етап, учасник, час, місце, бонус
- `Penalty` (штраф) — учасник, етап, тип, величина в секундах або очках, стан

| Рядок паспорта | Значення |
|---|---|
| «Один до багатьох» | `Team` → `Entry`; `Entry` → `Penalty` |
| «Багато до багатьох» | `Stage` ↔ `Entry` через `StageResult` |
| Ключова операція | `POST /stages/{id}/approve` — затвердити протокол етапу |
| Що змінюється в одній транзакції | `Stage.State` → `Approved`; `Entry.TotalTime` і `Entry.Points` для кожного учасника; `Team.TotalTime` перераховано; `Penalty.State` → `Applied` для штрафів етапу |
| Сценарій конкурентності | секретар затверджує етап, поки суддя вносить штраф тому самому учасникові: штраф або зникає, або застосовується двічі |
| Ідемпотентна операція | `PUT /entries/{n}/team` — перезакріпити стартовий номер за командою |
| Неідемпотентна | затвердження етапу: повторний виклик додає час етапу до загального заліку вдруге |
| Ролі | `chief-judge` — затверджує і анулює будь-який етап; `stage-secretary` — вносить результати лише свого етапу; `team-manager` — бачить штрафи своєї команди і подає протести |
| Що означає «своє» | `Stage.SecretaryId` для секретаря; `Entry.TeamId` для представника команди |
| Кешований ресурс | `GET /classification/general` — генеральна класифікація (публічна) |
| Некешований | `GET /stages/{id}/live` — проміжні відсічки під час етапу |
| Навантаження на читання | на фініші етапу генеральну класифікацію відкривають усі глядачі водночас, і вона має оновитися рівно в мить затвердження |
| Зовнішня залежність | отримання відсічок із системи хронометражу (заглушка) |
| Чутливий атрибут | `Entry.LicenseNumber` |
| Сутність зі станом | `Stage`: `Planned → Running → ResultsDraft → Approved / Annulled` |

На відміну від домену 17, тут одне затвердження перераховує рядки для всіх учасників одразу — це готовий матеріал для демонстрації N+1 і проєкції в ЛР2.

### 19. Приймання зерна на елеваторі

*Природа: сільське господарство. Складність: ★★☆*

Елеватор приймає автомобільні партії зерна: лабораторія визначає показники якості й товарний клас, після чого партію розміщують у силос відповідної групи. Оформлення приймання збільшує залишок силосу, закриває партію і поповнює рядок зберігання поклажодавця.

**Сутності**

- `Depositor` (поклажодавець) — код, назва, контактний телефон
- `Silo` (силос) — номер, місткість у тоннах, зберігається тонн, товарна група, стан
- `Delivery` (автомобільна партія) — умовний номер накладної, поклажодавець, культура, вага нетто, стан
- `QualityCheck` (лабораторний аналіз) — партія, вологість, смітна домішка, натура, клас, стан
- `StorageLine` (рядок зберігання) — поклажодавець, силос, культура, клас, тонн

| Рядок паспорта | Значення |
|---|---|
| «Один до багатьох» | `Depositor` → `Delivery`; `Delivery` → `QualityCheck` |
| «Багато до багатьох» | `Depositor` ↔ `Silo` через `StorageLine` |
| Ключова операція | `POST /deliveries/{id}/accept` — прийняти партію в силос |
| Що змінюється в одній транзакції | `Delivery.State` → `Accepted` із заліковою вагою; `Silo.StoredTons` += вага; `StorageLine` створено або збільшено; `QualityCheck.State` → `Applied` |
| Сценарій конкурентності | двоє вагарів приймають дві машини в силос, де лишилося місце на одну |
| Ідемпотентна операція | `PUT /silos/{n}/group` — встановити товарну групу порожнього силосу |
| Неідемпотентна | приймання: повторний виклик додає ту саму вагу вдруге |
| Ролі | `weighbridge-operator` — оформлює приймання будь-якої партії; `lab` — вносить лише показники якості; `depositor-clerk` — бачить лише свої рядки зберігання |
| Що означає «своє» | `StorageLine.DepositorId` збігається з ідентифікатором поклажодавця в токені |
| Кешований ресурс | `GET /silos` — паспорт силосів і товарні групи |
| Некешований | `GET /silos/{n}/free-capacity` — вільна місткість |
| Навантаження на читання | у жнива черга машин на вагах і кабінети поклажодавців безперервно опитують стан елеватора — читань на порядки більше, ніж приймань |
| Зовнішня залежність | перевірка накладної в зовнішньому реєстрі перевезень (заглушка) |
| Чутливий атрибут | `Depositor.Phone` |
| Сутність зі станом | `Delivery`: `Weighed → Sampled → Accepted / Rejected → Unloaded` |

### 20. Наряди на польові роботи

*Природа: сільське господарство. Складність: ★★☆*

Агроном видає наряди на обробіток полів: агрегат, партія препарату і норма внесення на гектар. Закриття наряду списує препарат із залишку партії, звільняє агрегат і вносить запис в історію обробітків поля.

**Сутності**

- `Field` (поле) — умовний кадастровий код, площа, культура сезону, дата останнього обробітку, стан
- `Machine` (агрегат) — інвентарний номер, тип, ширина захвату, стан
- `ChemicalLot` (партія препарату) — артикул, назва, залишок у літрах, термін придатності, клас небезпеки
- `Operator` (механізатор) — табельний номер, допуск до робіт із препаратами, службовий телефон
- `FieldTask` (наряд) — поле, агрегат, партія препарату, механізатор, норма на гектар, площа завдання, стан
- `TreatmentRecord` (запис обробітку) — поле, партія препарату, дата, фактична площа, фактична доза

| Рядок паспорта | Значення |
|---|---|
| «Один до багатьох» | `Field` → `FieldTask` |
| «Багато до багатьох» | `Field` ↔ `ChemicalLot` через `TreatmentRecord` |
| Ключова операція | `POST /tasks/{id}/close` — закрити наряд на обробіток |
| Що змінюється в одній транзакції | `FieldTask.State` → `Done`; `ChemicalLot.RemainingLitres` -= норма × фактична площа; `Machine.State` → вільний; новий `TreatmentRecord` і `Field.LastTreatmentDate` |
| Сценарій конкурентності | два механізатори закривають наряди на різні поля з однієї партії препарату, якої лишилося на одне поле |
| Ідемпотентна операція | `PUT /fields/{code}/crop` — встановити культуру сезону |
| Неідемпотентна | закриття наряду: повторний виклик списує препарат удруге |
| Ролі | `agronomist` — видає і закриває будь-які наряди; `operator` — закриває лише свої; `storekeeper` — веде партії препаратів і терміни придатності |
| Що означає «своє» | `FieldTask.OperatorId` збігається з табельним номером у токені |
| Кешований ресурс | `GET /fields` — реєстр полів із площами й культурами сезону |
| Некешований | `GET /chemical-lots/{sku}/remaining` — залишок препарату |
| Навантаження на читання | планшети в полі вранці синхронізують реєстр полів і препаратів, і всі бригади роблять це в одну годину |
| Зовнішня залежність | прогноз вітру й опадів для допуску до обприскування (заглушка) |
| Чутливий атрибут | `Operator.Phone` |
| Сутність зі станом | `FieldTask`: `Planned → Issued → InWork → Done / Cancelled` |
