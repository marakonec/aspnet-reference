# ADR-003. Делегована автентифікація і авторизація за ресурсом

**Статус:** ухвалено. **Дата:** 03.11.2026. **Тег:** stage-4-v2026.

## Контекст

Видавати прилади може лише оператор. Замовник бачить і створює лише власні бронювання. Застосунок не повинен зберігати паролі користувачів.

## Рішення

Користувачів і ролі веде сервер ідентичності Keycloak, область імпортується з файлу `infra/keycloak/app-realm.json`. Застосунок приймає токен доступу JWT і перевіряє підпис, видавця, аудиторію `app-api` і строк без допуску на розбіжність годинників. Роль береться із заяви `roles`, власник із заяви `owner_id`, яку відображувач Keycloak заповнює з атрибута користувача. Рішення про доступ до бронювання ухвалює обробник політики після читання ресурсу (`Security/ReservationAccess.cs`). Для переліку бронювань рішення стає фільтром запиту. Власника нового бронювання замовник не вказує, його бере застосунок із токена. Відмова автентифікації дає 401 із заголовком `WWW-Authenticate`, відмова авторизації 403 без подробиць про чужі дані, причина пишеться в лог.

## Розглянуті альтернативи

| Альтернатива | Причина відхилення |
|---|---|
| Власні облікові записи в застосунку (ASP.NET Core Identity) | Застосунок починає зберігати паролі і відповідати за їх захист, вхід через зовнішнього постачальника стає окремою задачею |
| Авторизація лише за роллю | Замовник із роллю `customer` отримав би доступ до будь-якого бронювання |
| Ключі API для клієнтів | Ключ не несе ідентичності користувача, «своє» визначити неможливо |

## Наслідки

Без сервера ідентичності застосунок не приймає жодного захищеного запиту. Скрипти перевірки отримують токени потоком паролів через окремі тестові клієнти, у вебклієнта цей потік вимкнено. Перейменування атрибута власника потребує зміни відображувача в файлі області і константи `OwnerIdClaim`.

## Чим підтверджено

| Твердження | Метод перевірки | Результат | Висновок |
|---|---|---|---|
| Кожна операція, крім каталогу, вимагає токена | самоперевірка, перевірка 3.1 | 401 із `WWW-Authenticate` для всіх захищених операцій | контракт і код узгоджені |
| Прострочений токен, токен іншого видавця, іншої аудиторії і зі зміненим підписом відхиляються | `.\scripts\negative.ps1`, рядки N1–N4 | 401 для кожного | перевіряються всі чотири ознаки |
| Замовник не читає чуже бронювання | самоперевірка 3.3, `negative.ps1` N5 | 403 в описі проблеми | авторизація за ресурсом працює |
| Замовник бачить у переліку лише свої бронювання | тест `Customer_lists_only_own_reservations` | у переліку лише `cus-2` | фільтр запиту працює |
